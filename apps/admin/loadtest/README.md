# লোড টেস্ট (k6)

১,০০০ দোকানের ব্যস্ত সময়ে স্টোরফ্রন্ট থেকে আমাদের সার্ভারে যত অনুরোধ আসে, তা নকল করে পাঠানো হয়:
Web Pixel, উইজেটের view/click, রিভিউ, Recent Sales, Live Chat-এর খোঁজ, আর `orders/paid` ও
`checkouts/update` webhook। এতে নেই:

- থিমের ফাইল আর উইজেটের কনফিগ: Shopify-র CDN থেকে যায়, আমাদের সার্ভারে আসে না।
- অ্যাডমিনের পাতা: মার্চেন্ট নিজে ব্যবহার করেন, ভিজিটরের তুলনায় খুব কম।
- AI আর ইমেইল পাঠানো: বাইরের সেবায় যায়, তাদের নিজেদের সীমা আছে।

## ট্রাফিকের অনুমান

| পরিবর্তনশীল               | ডিফল্ট | মানে                                                       |
| ------------------------- | ------ | ---------------------------------------------------------- |
| `STORES`                  | 1000   | দোকানের সংখ্যা                                             |
| `SESSIONS_PER_STORE_DAY`  | 2000   | একটা দোকানে দিনে গড় ভিজিট                                 |
| `PAGES_PER_SESSION`       | 4      | প্রতি ভিজিটে পাতা                                          |
| `SESSION_SECONDS`         | 180    | একটা ভিজিট কতক্ষণ খোলা থাকে (Live Chat-এর খোঁজের জন্য)     |
| `PEAK_FACTOR`             | 3      | ব্যস্ত সময়ে গড়ের কত গুণ                                  |
| `ORDERS_PER_STORE_DAY`    | 30     | দিনে অর্ডার                                                |
| `CHECKOUTS_PER_STORE_DAY` | 100    | দিনে চেকআউট শুরু (প্রতিটায় গড়ে তিনটা `checkouts/update`) |
| `SCALE`                   | 1      | পুরো হিসাবের কত অংশ চালানো হবে (0.5 মানে অর্ধেক)           |
| `DURATION`                | 10m    | কতক্ষণ চলবে                                                |

ডিফল্টে প্রতি সেকেন্ডে মোট প্রায় ৭২০টা অনুরোধ: পিক্সেল ২৭৮, উইজেটের ইভেন্ট ২২২, Live Chat ১২৫,
রিভিউ ৫৬, Recent Sales ২৮, webhook ১১। বেশিরভাগ দোকানে দিনে ২,০০০ ভিজিট হয় না, তাই এই হিসাব
ইচ্ছে করেই বেশির দিকে; এতে পাস করলে আসল ট্রাফিকে জায়গা থাকে।

## কোথায় চালাবেন

- শুধু স্টেজিং বা নিজের কম্পিউটারের ডাটাবেসে। `seed.mjs` ১,০০০টা নকল দোকান বানায়; আসল ডাটাবেসে কখনো নয়।
- k6 চালান সার্ভার থেকে আলাদা একটা কম্পিউটারে। একই মেশিনে চালালে k6 নিজেই সার্ভারের CPU খায়, তখন
  মাপটা মেশিনের, অ্যাপের নয়।
- [k6 ইনস্টল](https://grafana.com/docs/k6/latest/set-up/install-k6/) করে নিন।

## ধাপ

সব কমান্ড `apps/admin` ফোল্ডার থেকে।

1. **স্টেজিং-এ IP-র সেটিং এক বাড়ান।** k6 প্রতিটা অনুরোধে আলাদা নকল ভিজিটর IP পাঠায়, কিন্তু হোস্টিং-এর
   প্রক্সি তার পাশে k6 মেশিনের নিজের IP যোগ করে। সাধারণ সেটিং-এ সব অনুরোধ তাই এক IP থেকে আসা মনে হয়,
   রেট লিমিট লেগে যায় (429) আর টেস্ট ব্যর্থ হয়। টেস্টের সময়টুকু `TRUSTED_PROXY_COUNT` স্বাভাবিকের চেয়ে
   এক বেশি দিন (ফাঁকা মানে 1, তাই 2) আর `CLIENT_IP_HEADER` ফাঁকা রাখুন। নিজের কম্পিউটারে প্রক্সি নেই,
   সেখানে কিছু বদলাতে হয় না।
2. **নকল দোকান বানান** (স্টেজিং ডাটাবেসের `DATABASE_URL` দিয়ে):

   ```sh
   LOADTEST_SEED=yes node loadtest/seed.mjs --stores 1000
   ```

   Windows PowerShell-এ: `$env:LOADTEST_SEED="yes"; node loadtest/seed.mjs --stores 1000`

3. **ছোট করে শুরু করুন।** `SHOPIFY_API_SECRET` হবে স্টেজিং সার্ভারের app secret, নইলে সই মেলে না।
   secret কমান্ডে না লিখে environment-এ রাখুন, k6 সেখান থেকেই পড়ে:

   ```sh
   export SHOPIFY_API_SECRET=...
   k6 run -e BASE_URL=https://staging.example.com -e SCALE=0.05 -e DURATION=1m loadtest/storefront.js
   ```

   সব check পাস করলে `SCALE=0.5`, তারপর `SCALE=1` (১০ মিনিট)।

4. **শেষে মুছে ফেলুন আর সেটিং ফেরত দিন:**

   ```sh
   LOADTEST_SEED=yes node loadtest/seed.mjs --clean
   ```

   `TRUSTED_PROXY_COUNT` আগের মানে ফেরত না দিলে ভিজিটর নকল IP দিয়ে রেট লিমিট এড়াতে পারবেন।

নকল দোকানগুলোর Shopify টোকেন আসল নয়। টেস্ট চলাকালীন কোনো পটভূমির কাজ এদের হয়ে Shopify-তে কল
করলে লগে ভুল দেখা যেতে পারে; তাই বানানোর পরপরই টেস্ট চালান আর শেষ হলেই মুছুন।

## ফলাফল কীভাবে পড়বেন

পাসের শর্ত (`storefront.js`-এর `thresholds`):

- ব্যর্থ অনুরোধ ১%-এর কম (429-ও ব্যর্থ ধরা হয়)
- স্টোরফ্রন্টের p95 ৩০০ms-এর নিচে, p99 ১ সেকেন্ডের নিচে
- webhook-এর p95 ১ সেকেন্ডের নিচে
- `dropped_iterations` ১০০-র কম: বেশি হলে সার্ভার (বা k6-এর মেশিন) তাল রাখতে পারেনি

অনেক 429 এলে আগে ১ নম্বর ধাপের সেটিং দেখুন।

## মাপা ফল (২০২৬-১১-১৬)

একটা ৪ vCPU, ১৬ GB Linux মেশিনে সার্ভার (`react-router-serve`, `NODE_ENV=production`),
PostgreSQL 16 আর k6 তিনটাই একসাথে; ডাটাবেসে ১,০০০টা দোকান।

| লোড              | সেকেন্ডে অনুরোধ    | p95        | ব্যর্থ | ফল                      |
| ---------------- | ------------------ | ---------- | ------ | ----------------------- |
| ৫%               | ~৩৬                | ১২ms       | ০      | পাস                     |
| ৫০%              | ~৩৬০               | ১৮ms       | ০      | পাস                     |
| ৬০%              | ~৪৩০               | ৩৫ms       | ০      | পাস                     |
| ৭০%, এক প্রসেস   | ~৪৯০ (চাওয়া ~৫০০) | ০.৭–১.৩s   | ০      | ব্যর্থ: প্রসেস পুরো ভরা |
| ১০০%, এক প্রসেস  | ~৪৯০ (চাওয়া ~৭২০) | ১.৯s       | ৬.৫%   | ব্যর্থ                  |
| ১০০%, দুই প্রসেস | ~৫৮৫               | ৩s-এর বেশি | ০      | ব্যর্থ: মেশিন ভরা (৮৬%) |

যা জানা গেল:

- এক Node প্রসেস আরামে সেকেন্ডে ~৪৩০ অনুরোধ নেয় (৬০%, মানে প্রায় ৬০০ দোকানের ব্যস্ত সময়), সর্বোচ্চ
  ~৪৯০। সীমাটা Node-এর একটা JavaScript থ্রেড; তার বড় অংশ যায় Prisma-র কাজে আর রাউটিং-এ।
- ডাটাবেস বাধা নয়: ৭০% লোডেও PostgreSQL মাত্র ~০.৩ CPU core ব্যবহার করেছে।
- দুই প্রসেসের মাপ মেশিনের সীমা, অ্যাপের নয় (অ্যাপ ২.৪, PostgreSQL ০.৫, k6 ০.৪ core)। পুরো লোড
  আলাদা মেশিনে, স্টেজিং-এ মাপা বাকি; পাবলিক লঞ্চের আগে করতে হবে।

## Production-এ যা লাগবে

- **প্রতি ~৫০০ দোকানে একটা অ্যাপ প্রসেস, সাথে একটা বাড়তি**: ১,০০০ দোকানে ৩টা, যাতে একটা বন্ধ থাকলেও
  (deploy বা ক্র্যাশ) ব্যস্ত সময় চলে। প্রতিটা প্রসেসের জন্য ২ vCPU: JavaScript এক core নেয়, Prisma-র
  ইঞ্জিন আরেকটা। হোস্টিং-এ আলাদা instance, বা এক সার্ভারে PM2-এর cluster mode।
- **ডাটাবেসের সংযোগ**: প্রতিটা প্রসেস `DATABASE_URL`-এর `connection_limit` পর্যন্ত সংযোগ খোলে
  (না দিলে CPU × 2 + 1)। সব প্রসেস মিলে ডাটাবেসের `max_connections`-এর নিচে থাকতে হবে।
- **পটভূমির কাজ প্রতিটা প্রসেসে চলে**, তাতে সমস্যা নেই: কাজ আর ইমেইল `FOR UPDATE SKIP LOCKED` দিয়ে
  একজনই নেয়, ক্যাম্পেইন একবারই শুরু হয়, win-back একই অর্ডারের জন্য একবারই যায়।
- **রেট লিমিট প্রতিটা প্রসেসের নিজের মেমরিতে**: N প্রসেসে একজন ভিজিটর সর্বোচ্চ N গুণ অনুরোধ করতে পারেন।
  কয়েকটা প্রসেসে এটা ঠিক আছে; কড়া এক সীমা লাগলে লিমিট Redis-এ সরাতে হবে (`docker-compose.yml`-এ
  Redis আছে, কোড এখনো ব্যবহার করে না)।
- **লগ**: production-এ Shopify লাইব্রেরি এখন শুধু সতর্কতা আর ভুল লেখে; আগে প্রতিটা স্টোরফ্রন্ট অনুরোধে
  একটা লাইন হতো। খুঁজে দেখার দরকার হলে `SHOPIFY_LOG_LEVEL=info`।

ট্রাফিক আরও বাড়লে পরের ধাপ (এখন দরকার নেই): পিক্সেলের হিসাব মেমরিতে জমিয়ে কয়েক সেকেন্ড পরপর একসাথে
লেখা, App Proxy-র রাস্তায় দোকানের তথ্য ক্যাশ করা, আর পরিকল্পনামতো পিক্সেলের জন্য আলাদা Go সার্ভিস।

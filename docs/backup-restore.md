# ডাটাবেসের ব্যাকআপ আর রিস্টোর

অ্যাপের নিজের সব তথ্য PostgreSQL-এ থাকে: দোকানের সেটিংস, রিভিউ, সাবস্ক্রাইবার আর ইমেইলের লাইন,
পরিসংখ্যান, Shopify-র session। এগুলো হারালে মার্চেন্টদের কাজ হারায়, তাই তিন স্তরে রক্ষা করা হয়।

ডাটাবেসের বাইরে যা আছে:

- R2-র ফাইল (Visitor Recordings, AI-র ছবি আর ভিডিও): R2 নিজেই একাধিক জায়গায় রাখে।
- অর্ডার, প্রোডাক্ট আর গ্রাহক: Shopify-তেই থাকে।
- `.env`-এর চাবি (Shopify secret, API key, `BACKUP_KEY`): এগুলো ব্যাকআপে নেই; password manager-এ আলাদা
  কপি রাখুন।

## তিন স্তর

1. **হোস্টিং-এর নিজের ব্যাকআপ আর point-in-time recovery (PITR)।** managed PostgreSQL বাছাইয়ের সময়
   চালু করুন, অন্তত ৭ দিনের। এতে কয়েক মিনিট আগের অবস্থায় ফেরা যায়; আসল বিপদে এটাই প্রথম ভরসা।
2. **প্রতি রাতে নিজেদের ব্যাকআপ, হোস্টিং-এর বাইরে।** `scripts/db-backup.mjs` দিয়ে, আলাদা একটা
   private R2 bucket-এ। হোস্টিং-এ বড় সমস্যা হলে বা অ্যাকাউন্ট হারালেও কপি থাকে।
3. **রিস্টোর মহড়া।** প্রতি মাসে একবার শেষ ব্যাকআপ নতুন ডাটাবেসে ফিরিয়ে দেখা (নিচের ধাপ)। CI প্রতিটা
   PR-এ ছোট একটা ডাটাবেসে একই কাজ করে (`backup-restore` job), তাই স্ক্রিপ্ট বা migration ভাঙলে আগেই
   ধরা পড়ে।

## ব্যাকআপ নেওয়া

লাগবে Node 22, অ্যাপের dependency (`pnpm install`), আর ডাটাবেসের সংস্করণের সমান বা নতুন PostgreSQL
client tools (`pg_dump`, `pg_restore`)। টুলগুলো PATH-এ না থাকলে (যেমন Windows-এ) `PG_BIN`-এ তাদের
ফোল্ডার দিন, যেমন `C:\Program Files\PostgreSQL\16\bin`।

### এনক্রিপশনের চাবি (একবারই)

ব্যাকআপ সবসময় এনক্রিপ্ট হয় (AES-256-GCM), কারণ তাতে ক্রেতাদের ইমেইল, নাম আর ফোন থাকে, আর Shopify-র
protected customer data-র শর্তে ব্যাকআপ এনক্রিপ্ট করা বাধ্যতামূলক
([protected-customer-data.md](protected-customer-data.md))। চাবি একবার বানান:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

- আসা লেখাটা সার্ভারের `.env`-এ `BACKUP_KEY=...` হিসেবে রাখুন, আর একটা কপি password manager-এ।
- চাবি হারালে কোনো ব্যাকআপই আর খোলা যায় না, তাই password manager-এর কপিটাই আসল ভরসা।
- চাবি কখনো ব্যাকআপের bucket-এ, রিপোজিটরিতে বা ব্যাকআপের পাশে রাখবেন না।
- চাবি বদলাতে চাইলে নতুন চাবি দিন; পুরনো ব্যাকআপ খুলতে পুরনো চাবিটাও ৩০ দিন রেখে দিন।

```sh
cd apps/admin
DATABASE_URL="postgresql://..." BACKUP_KEY="..." node scripts/db-backup.mjs --out /var/backups/allinone --keep 14
```

- ঠিকানা হবে ডাটাবেসের **সরাসরি** ঠিকানা, pooler (pgbouncer) নয়।
- দুটো ফাইল তৈরি হয়: `<ডাটাবেস>-<সময়>.dump.enc` আর একই নামের `.json` (প্রতিটা টেবিলের সারি, migration,
  sha256, আর চাবির ছোট পরিচয় `keyId`)। দুটো সবসময় একসাথে রাখুন; `.json` ছাড়া রিস্টোর হয় না। `.json`-এ
  ক্রেতার কোনো তথ্য নেই।
- `pg_dump`-এর আউটপুট সরাসরি এনক্রিপ্ট হয়ে ফাইলে যায়; খোলা ব্যাকআপ কখনো ডিস্কে নামে না।
- `BACKUP_KEY` না থাকলে স্ক্রিপ্ট থেমে যায়। শুধু নিজের কম্পিউটারে, পরীক্ষার কপির জন্য `--unencrypted`
  দিলে এনক্রিপশন ছাড়া `.dump` হয়; সেটা কখনো সার্ভারে বা bucket-এ রাখবেন না।
- সারি গোনা আর ব্যাকআপ একই মুহূর্তের ছবি দেখে, তাই অ্যাপ চালু রেখেই নেওয়া যায়।
- `--keep 14` ফোল্ডারে শেষ ১৪টা রাখে, পুরনোগুলো মোছে।

### প্রতি রাতে, হোস্টিং-এর বাইরে কপি

হোস্টিং ঠিক হলে সেখানকার cron বা scheduled job-এ বসাতে হবে। Linux সার্ভারে উদাহরণ (প্রতি রাত ৩:৩০ UTC):

```cron
30 3 * * * cd /srv/allinone/apps/admin && set -a && . ./.env && set +a && node scripts/db-backup.mjs --out /var/backups/allinone --keep 7 && rclone copy /var/backups/allinone r2-backups:allinone-db-backups
```

- R2-তে আলাদা একটা private bucket (যেমন `allinone-db-backups`), আর শুধু সেই bucket-এ লেখার অনুমতিসহ
  আলাদা API token। অ্যাপের রেকর্ডিংয়ের bucket বা চাবি এখানে ব্যবহার করবেন না।
- bucket-এ lifecycle rule দিন: ৩০ দিনের পুরনো ফাইল নিজে থেকে মুছে যাবে।
- `rclone`-এ R2 যোগ করার নিয়ম: <https://rclone.org/s3/#cloudflare-r2>
- ব্যাকআপ ব্যর্থ হলে কমান্ড exit code 1 দেয়; হোস্টিং-এর alert বা ইমেইলে সেটা জানানোর ব্যবস্থা রাখুন।

### গোপনীয়তা

ব্যাকআপে ক্রেতাদের ইমেইল, নাম আর ফোন থাকে। তাই:

- ফাইল এনক্রিপ্ট করা, তাই bucket বা তার token ফাঁস হলেও চাবি ছাড়া কেউ পড়তে পারে না। একটা বাইটও বদলালে
  রিস্টোর খুলতে অস্বীকার করে।
- তবু শুধু private bucket আর সার্ভারে রাখুন। মহড়াও সার্ভারে একটা নতুন ডাটাবেসে করুন; প্রোডাকশনের ব্যাকআপ
  নিজের কম্পিউটারে নামাবেন না, কারণ Shopify-র শর্তে test আর production ডেটা আলাদা রাখতে হয়। রিপোজিটরিতে
  `backups/`, `*.dump` আর `*.dump.enc` gitignore করা আছে।
- ৩০ দিনের বেশি রাখবেন না: কোনো দোকান বা ক্রেতা তথ্য মুছতে বললে (GDPR redact) তা ৩০ দিনের মধ্যে
  ব্যাকআপ থেকেও চলে যায়। Privacy Policy-তে এই সময়টা লিখতে হবে।

## রিস্টোর (মহড়া বা আসল বিপদে)

1. নতুন, খালি একটা ডাটাবেস বানান (হোস্টিং-এর console-এ, বা `createdb allinone_restored`)। স্ক্রিপ্ট
   খালি নয় এমন ডাটাবেসে কখনো লেখে না।
2. ব্যাকআপ আর তার `.json` একই ফোল্ডারে রাখুন, তারপর যে চাবিতে ব্যাকআপ হয়েছিল সেটা দিয়ে:

   ```sh
   cd apps/admin
   BACKUP_KEY="..." node scripts/db-restore.mjs /path/allinone-20261117T033000Z.dump.enc --into "postgresql://.../allinone_restored"
   ```

   স্ক্রিপ্ট আগে ফাইলের sha256 মেলায় (ক্ষতিগ্রস্ত বা অর্ধেক কপি থামায়) আর চাবিটা ঠিক কিনা দেখে, তারপর
   একটা অস্থায়ী ফোল্ডারে খোলে (জায়গা কম হলে `TMPDIR` দিয়ে অন্য ফোল্ডার দিন), ফেরত আনে, `ANALYZE`
   চালায়, আর প্রতিটা টেবিলের সারি আর migration ব্যাকআপের সাথে মেলায়। খোলা কপিটা শেষে সবসময় মুছে যায়।
   কিছু না মিললে exit code 1 আর "Do not use this database"।

3. মহড়া হলে এখানেই শেষ: সময়, ফাইলের আকার আর ফল লিখে রাখুন, তারপর ডাটাবেসটা মুছে দিন। মহড়ায় যে
   সময় লাগে, আসল বিপদেও মোটামুটি ততটাই লাগবে।

### আসল বিপদে অ্যাপ নতুন ডাটাবেসে সরানো

1. PITR থাকলে আগে সেটা দিয়ে চেষ্টা করুন: তাতে কয়েক মিনিটের বেশি তথ্য হারায় না।
2. না হলে সব অ্যাপ প্রসেস বন্ধ করে ওপরের মতো সবচেয়ে নতুন ব্যাকআপ রিস্টোর করুন।
3. `DATABASE_URL` নতুন ডাটাবেসে দিন, `pnpm run setup` চালান (কোড ব্যাকআপের চেয়ে নতুন হলে বাকি
   migration বসায়), তারপর অ্যাপ চালু করুন।
4. দেখে নিন: অ্যাডমিন খোলে, একটা দোকানের উইজেট আসে, আর নতুন webhook পৌঁছায়।
5. Shopify ব্যর্থ webhook ৪ ঘণ্টায় ৮ বার আবার পাঠায়। অ্যাপ ৪ ঘণ্টার কম বন্ধ থাকলে সেই সময়ের অর্ডার আর
   গ্রাহকের খবর নিজে থেকেই আসে।
6. শেষ ব্যাকআপ আর বিপদের মাঝের তথ্য (রিভিউ, নতুন সাবস্ক্রাইবার, পরিসংখ্যান) রাতের ব্যাকআপে থাকে না।
   সাবস্ক্রাইবার Email Marketing-এর "Import from Shopify" দিয়ে ফেরত আনা যায়; বাকিগুলোর জন্যই PITR দরকার।
